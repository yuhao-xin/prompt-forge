## 它解决什么问题

用 AI 最大的障碍不是**不会写提示词**，而是**说不清三件事**：

| 说不清的 | 后果 |
|---|---|
| 要做成什么样（完成标准） | AI 交付了，你不知道算不算完成，只能凭感觉 |
| 不给什么（红线） | 每次都要在结果里挑出"又来了"的毛病 |
| 给谁用（受众） | 语气、深度、举例全靠 AI 猜 |

PromptForge 像一位 **AI 产品工程师**，通过对话式追问逼出这三件事，按结构化模板现场生成提示词，
再逼你回答最后一问——**"你打算拿什么真实输入去试它？"**——
然后带着五维体检和反馈闭环，把提示词打磨到能直接用。

> **核心定位不是"教新人写提示词"，而是「经验 → 提示词资产」的转化器。**
> 追问引擎服务被引导的一端，体检与验收保证产出的一端。

## 核心流程：一次提示词打磨 = 一个迷你 AI 产品流程

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│  接  单  │  澄  清  │  生  成  │  评  测  │  交  付  │
│ 分接器   │ 产品经理 │  架构师   │ 测试工程师│  交付物  │
└──────────┴──────────┴──────────┴──────────┴──────────┘
      │          │          │          │          │
   意图分类   问题树追问  模板引擎   五维体检   提示词包
   +置信度    每次一个    五件套     按分差补强  +接入指引
   +理由可见  可跳过                            +验收用例
```

| 阶段 | 产品团队角色 | 工具行为 |
|---|---|---|
| 接单 | 分接器 | 关键词权重打分路由到 8 类任务；多意图时列出候选让用户确认；**判定理由可见** |
| 澄清 | 产品经理 | 问题树每次只问一个、选项式优先、全部可跳过、轮次硬上限；每问带"为什么问这个" |
| 生成 | 架构师 | 五件套模板填充（角色/目标/规则/格式/示例） |
| 评测 | 测试工程师 | 自动自检 + 独立体检模式，按分差给补强建议 |
| 迭代 | badcase 驱动 | GSB → 差评必选原因 → **按模块重写**而非笼统重生成 |
| 交付 | 交付物 | Markdown / JSON 提示词包 + 接入指引 + 验收用例 |

## 特性

### 1. 任务分接器 —— 把不确定性变成功能
关键词权重打分路由，三种结果：强命中直接定、多意图列候选让你确认、全无命中走通用兜底。
**关键是判定理由对用户可见**（"命中了：论文、方法"），误判时你能立刻发现并纠正。

### 2. 追问引擎 —— 每次只问一个
选项式优先（降低表达负担）、全部可跳过（用推荐值并标注）、轮次硬上限（防止无限循环）、
可回退上一题。每个问题都带 **「为什么问这个」** 折叠说明——透明化，顺便教会用户提示词思维。

### 3. 实时提示词卡片 —— 黑盒变白盒
右侧卡片随你的每一个回答**逐格填充**，槽位完成度可见。你亲眼看着提示词被一锤一锤锻出来。

### 4. 就地改写 —— 闭环的最后一步
生成后点卡片任意一段可直接编辑（Ctrl/Cmd+Enter 保存、Esc 取消、可还原为模板输出），
改完**自动重新体检**。用户在外面改完的经验不会再流失。

### 5. 验收用例 —— 把"能用"从口号变成可判定
生成后追问"你打算拿什么真实输入去试它？"，写进导出包的「验收用例」节，包含：
真实输入、通过判定（同时满足完成标准且不违反明确不做）、不通过怎么办。

### 6. 五维体检 —— 结构分也可解释
角色 / 任务 / 约束 / 格式 / 示例 各 0-2 分，**每维展示"检测到 N 处信号"**，不是黑箱打分。

### 7. 误判纠错 —— 为"AI 会错"而设计
分接器拿不准时会问你；事后觉得归类错了，可**「换个类型重锻」且保留已填内容**——
纠错 ≠ 从头再来。

### 8. 经验库 —— 越用越懂你
每次锻造完成，你亲口回答的偏好会自动沉淀（受众 / 风格 / 常用约束 / 明确不做 / 技术栈 / 场合），
带频次与来源。下次开炉**自动预填**并标注「来自经验」。可查看、删除、导出、换设备导入。

## 项目结构

```
prompt-forge/
├── index.html            # 单页结构
├── styles.css            # 暗色「锻造台」主题
├── data.js               # 策略库：8 任务类型 × 问题树 × 模板 × 体检规则
├── storage.js            # 持久化抽象层：能力探测 / 损坏自愈 / 容量降级
├── experience.js         # 经验库：跨会话画像沉淀与预填
├── app.js                # 状态机 + 分接器 + 追问引擎 + 体检 + 导出
├── validate-data.js      # 策略库一致性校验
├── test-harness.js       # 全流程功能回归（DOM 桩）
├── eval-runner.js        # 三场景产出评估（导出产物存档）
├── docs/
│   ├── 01-设计总纲.md     # 定位、调研结论→设计决策、信息架构
│   ├── 02-策略库设计.md   # 任务类型、问题树五原则、体检规则、验收清单
│   └── 03-PM审计与补缺清单.md  # AI 产品经理视角审计
└── eval-output/          # 评估产物存档
```

**架构原则**：单一数据源（`state`），所有 UI 从 `state` 派生；
分层为 数据层（策略库）→ 逻辑层（状态机）→ 渲染层；持久化统一经 `storage.js`。

## 测试

```bash
node validate-data.js    # 策略库一致性校验（槽位闭环、默认值兜底、正则可编译）
node test-harness.js     # 全流程功能回归：8 个场景 + 9 条路由
node eval-runner.js      # 三场景产出评估，产物存档到 eval-output/
```

三层各有分工：

| 脚本 | 保证什么 |
|---|---|
| `validate-data.js` | 策略库**数据正确**（槽位不悬空、无空白段、正则合法） |
| `test-harness.js` | 交互**流程不崩**（分接 / 追问 / 重写 / 导出 / 刷新恢复） |
| `eval-runner.js` | 产物**质量可评估**（真实场景跑通并留档比对） |
